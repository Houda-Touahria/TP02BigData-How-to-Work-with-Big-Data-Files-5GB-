TP 02: Handling Large Datasets (+5GB) in PythonAuthor: Master 2 Student (AI & Data Science)Module: Big Data Analytics (2026/2027)University: University of Eloued — Faculty of Exact SciencesWhat is this lab about?In this practical work, the main goal was to test how standard Python tools handle datasets that exceed available RAM, and to compare alternative approaches for processing large-scale CSV files without crashing the machine.Specifically, we tested three approaches on a 5.5 GB eCommerce dataset:Classic Pandas loading (pd.read_csv) to see the Out-of-Memory behavior.Batch processing with Pandas chunks (chunksize=100_000) for incremental computation.Out-of-core computing using Dask to leverage multi-threading and lazy evaluation.Dataset & EnvironmentDataset: eCommerce behavior data from multi-category store (2019-Oct.csv).Raw file size: ~5.5 GB (around 42.45 million rows).Target metric: Global mean of product price.Execution setup: Kaggle Notebook environment (~31.35 GB allocated RAM, multi-core CPU).Walkthrough & Personal Observations1. The Standard Pandas Attempt (Memory Heavy)I first tried loading the whole CSV at once using standard pd.read_csv().What happened: The file eventually loaded after 184.50 seconds (~3 minutes), but RAM usage spiked drastically from 0.90 GB to 20.15 GB.Takeaway: Even though the file is only 5.5 GB on disk, Pandas creates Python objects, indexes, and type representations that bloated memory usage to over 20 GB. On a typical laptop with 8GB or 16GB of RAM, this causes an immediate MemoryError or freezes the entire OS.2. Stream Processing via ChunkingTo avoid the huge memory spike, I set chunksize = 100_000 to stream through the file row-by-row in batches.How I calculated the average: Instead of loading full series into memory, I kept running totals (total_sum += chunk['price'].sum() and total_count += chunk['price'].count()), letting Python garbage-collect each chunk before reading the next.Results:Peak RAM: Stayed flat around 4.81 GB.Execution time: 112.65 seconds.Calculated average price: 290.32 across 42,448,764 records.Takeaway: Much safer for low-memory machines, but because it processes sequentially on a single thread, it took nearly two minutes to finish.3. Scaling with Dask (Parallel & Lazy)Next, I switched to dask.dataframe.Lazy Evaluation in practice: Running dd.read_csv() and .mean() returned almost instantly because Dask doesn't compute anything upfront—it just creates a task graph (DAG).Parallel Execution: When I finally called .compute(), Dask split the workload across CPU cores and streamed partitions out-of-core.Results:Execution time: 65.68 seconds (roughly 1.7x faster than Chunking).RAM usage: Kept at a steady 5.77 GB.Calculated average price: 290.32 (identical to the Chunking result).Summary BenchmarkApproachMax Memory (RAM)Execution TimeHow it executedStandard Pandas20.15 GB184.50 sLoaded entire file in RAM; single-core (crashes on 8GB/16GB PCs)Pandas Chunking4.81 GB112.65 sSequential batches of 100k rows; very low memory footprintDask DataFrame5.77 GB65.68 sMulti-threaded lazy compute; best balance of speed and RAMFinal ThoughtsFor simple data piping or inserting rows into a database without extra dependencies, Pandas Chunking is very straightforward and dependable.For actual analytics and aggregation on large datasets, Dask is clearly the superior option. It keeps memory usage low like chunking, but cuts execution time almost in half by utilizing all CPU cores in parallel.
